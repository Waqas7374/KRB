# 07 — API Specification

REST, versioned at `/api/v1`. OpenAPI 3.1 generated by FastAPI at `/api/v1/openapi.json`, with
`/docs` (Swagger) and `/redoc`. The OpenAPI document is the **source of the TypeScript types** used
by both the web and mobile clients — `packages/api-types` is generated in CI and a drift check
fails the build.

---

## 1. Conventions

### Response envelopes

Single resource — the resource object itself, no wrapper:

```json
{ "id": "018f…", "po_number": "PO-2026-00184", "status": "APPROVED", … }
```

Collection — a consistent envelope:

```json
{
  "items": [ … ],
  "page": { "limit": 50, "offset": 0, "total": 247, "has_more": true },
  "meta": { "sort": "-created_at", "filters_applied": { "status": ["APPROVED"] } }
}
```

High-volume endpoints (deliveries, inventory ledger, audit log) additionally accept
`cursor=<opaque>` and return `page.next_cursor`. Offset paging past 10 000 rows is refused with a
pointer to the cursor form — deep offsets on a growing table are a performance trap.

### Query grammar

| Parameter | Form | Example |
|---|---|---|
| Filter | `field=value`, repeated for OR, `field__op=value` for operators | `status=APPROVED&status=SENT&total_amount__gte=100000` |
| Operators | `eq ne gt gte lt lte in nin like ilike isnull between` | `captured_at__between=2026-09-01,2026-09-21` |
| Sort | `sort=field` / `sort=-field`, comma-separated | `sort=-captured_at,truck_number` |
| Search | `q=` — per-endpoint documented field set, trigram-indexed | `q=RJ14` |
| Sparse fields | `fields=id,name,status` | |
| Expand | `expand=vendor,project` — a documented whitelist, never arbitrary | |

Unknown filter fields are a `422`, not silently ignored. Silently ignoring a filter is how a
user exports the wrong data and signs it.

### Headers

| Header | Purpose |
|---|---|
| `Authorization: Bearer <access>` | 15-minute access token |
| `Idempotency-Key` | Required on POST for financial/inventory-moving endpoints |
| `X-Request-ID` | Echoed into logs, errors and audit rows |
| `X-Company-ID` | Optional company selector for multi-company users |
| `If-Match` / `ETag` | Optimistic concurrency on mutable aggregates |

### Status codes

`200` ok · `201` created · `202` accepted (async export) · `204` no content ·
`400` malformed · `401` unauthenticated · `403` permission denied · `404` not found **or out of
scope** · `409` conflict / idempotency mismatch / version mismatch · `422` validation ·
`423` locked (closed accounting period) · `429` rate limited · `500` · `503`.

## 3. Worked example — approving a GRN

`POST /api/v1/grns/{id}/approve` with `Idempotency-Key`. In one transaction:

1. Authorise `grn.approve` + scope over the GRN's site.
2. Assert GRN status `PENDING_APPROVAL`, its approval request is APPROVED, the accounting period
   is OPEN, and `accepted + rejected = delivered` on every line.
3. Insert `inventory_transactions` (GRN_IN) per accepted line, with valuation.
4. Update `inventory_balances` under `SELECT … FOR UPDATE`; write `balance_*_after` back onto the
   ledger rows.
5. Release the matching `budget_commitments` and increment `budget_lines.actual_amount`.
6. Build the journal entry from `posting_rules` (Dr Inventory/Development Cost, Cr GRN Accrual),
   insert lines with the full dimension set, post it.
7. Update `purchase_order_items.received_quantity` / `accepted_quantity`; advance the PO status.
8. Update the source delivery to `RECEIVED` and stamp `grn_id`.
9. Write `audit_logs` and append `grn.approved` to `outbox_events`.

Returns `200` with the GRN, the created journal entry id, and the resulting balances. Any failure
rolls back all of it — there is no state in which stock moved but the GL did not.

## 4. Rate limiting

| Scope | Limit |
|---|---|
| `POST /auth/login` | 5 / 15 min per (ip, identifier), then exponential lockout |
| `POST /auth/password/forgot` | 3 / hour per identifier |
| `POST /sync/push` | 60 / min per device |
| Authenticated default | 600 / min per user |
| Report export | 10 / hour per user |

Redis token bucket; `429` carries `Retry-After`.

## 5. Versioning

`/api/v1` is frozen on additive changes only. Breaking changes go to `/api/v2` with both served
during a deprecation window — mobile clients in the field cannot be upgraded on demand, so the
server must tolerate an old app for at least one release cycle. `GET /version` plus a
`X-Min-App-Version` response header lets the app prompt for an upgrade when it genuinely must.
